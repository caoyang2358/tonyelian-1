# Copper Twin 运维部署文档

本文档适用于当前两个独立仓库：

- 前端：`Git_NTP_TYL_Web/CopperTwin-Portable`
- 后端：`Git_NTP_TYL_Mid`

推荐生产组合为 PostgreSQL 14+、Java 17、Maven 3.9+、Node.js 22.13+。如甲方使用 MySQL，可选 MySQL 5.7+ 适配 profile。Windows、Linux、macOS 均可部署；PostgreSQL 与 MySQL 使用各自的迁移目录和 SQL 文件。

## 一、目录与端口

| 服务 | 默认端口 | 生产进程 |
|---|---:|---|
| 后端 API | 8080 | Spring Boot 可执行 JAR |
| 前端 Web | 4173 | vinext start |
| PostgreSQL | 5432 | PostgreSQL 服务或 Docker |

浏览器只需要访问前端地址。前端通过 `NEXT_PUBLIC_API_BASE_URL` 调用后端。

## 二、部署前准备

### Linux/macOS

安装并确认：

```bash
java -version       # Java 17
mvn -version        # Maven 3.9+
node --version      # Node.js >= 22.13
psql --version      # PostgreSQL 客户端
```

### Windows PowerShell

```powershell
java -version
mvn -version
node --version
psql --version
```

时间统一使用服务器本地时间或显式的 `Asia/Shanghai` 时区。生产环境不要使用演示 profile。

## 三、数据库初始化

### 方式 A：完整 SQL（新机器推荐）

在 PostgreSQL 创建空数据库后执行：

```bash
createdb -h localhost -U copper_twin copper_twin
psql -h localhost -U copper_twin -d copper_twin \
  -f database/copper_twin_full.sql
```

Windows：

```powershell
createdb -h localhost -U copper_twin copper_twin
psql -h localhost -U copper_twin -d copper_twin -f database\copper_twin_full.sql
```

该文件包含最终表结构、约束、索引、演示种子数据以及 V8 幂等约束。只能对空库执行；已有业务库应先备份并使用 Flyway 升级。

### 方式 B：Flyway 随后端自动迁移

后端启动时会自动执行 `src/main/resources/db/migration/V*.sql`。只需要创建空数据库并配置连接信息，不要同时执行完整 SQL 和 Flyway。

### MySQL 5.7/8.0

MySQL 使用独立脚本：`database/copper_twin_mysql_schema.sql`（建表）和
`database/copper_twin_mysql_seed.sql`（演示种子数据）。也可只创建空库，让后端以
`mysql` profile 启动，Flyway 会执行 `src/main/resources/db/migration-mysql/V1__mysql_schema.sql`
和 `V2__mysql_seed.sql`。不要将 PostgreSQL 的 V1-V8 迁移脚本用于 MySQL。

```powershell
mysql -u root -p -e "CREATE DATABASE copper_twin CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root -p copper_twin < database\copper_twin_mysql_schema.sql
mysql -u root -p copper_twin < database\copper_twin_mysql_seed.sql
```

MySQL 连接配置必须包含 `serverTimezone=Asia/Shanghai`，后端使用统一 JDBC 时间转换将
MySQL `TIMESTAMP` 映射为 API 的 `OffsetDateTime`。MySQL 5.7 不强制执行 CHECK 约束，状态和范围校验由后端负责。

### Docker PostgreSQL

在后端仓库执行：

```bash
docker compose up -d postgres
docker compose ps
```

默认账号为 `copper_twin`，默认密码为 `copper_twin_dev`，仅适合开发/演示。生产环境必须修改密码、限制端口暴露并使用持久化卷。

## 四、后端配置、打包和运行

### 环境变量

复制 `后端/.env.example` 的内容到部署系统的环境变量中：

```text
SERVER_PORT=8080
DB_URL=jdbc:postgresql://127.0.0.1:5432/copper_twin
DB_USERNAME=copper_twin
DB_PASSWORD=请替换为强密码
CORS_ALLOWED_ORIGINS=http://127.0.0.1:4173
LOG_LEVEL=INFO
```

不要把真实密码提交到 Git。`DB_PASSWORD`、CORS 白名单和日志级别应由部署平台注入。

### Linux/macOS

```bash
cd Git_NTP_TYL_Mid
mvn -DskipTests package
java -jar target/backend-0.1.0-SNAPSHOT.jar
```

验证：

```bash
curl http://127.0.0.1:8080/api/v1/health/live
curl http://127.0.0.1:8080/api/v1/health/ready
```

### Windows PowerShell

```powershell
Set-Location Git_NTP_TYL_Mid
mvn -DskipTests package
$env:DB_URL='jdbc:postgresql://127.0.0.1:5432/copper_twin'
$env:DB_USERNAME='copper_twin'
$env:DB_PASSWORD='请替换为强密码'
java -jar target\backend-0.1.0-SNAPSHOT.jar
```

### 测试后端

```bash
mvn test
mvn package
```

测试使用 H2 内存数据库，不会连接生产 PostgreSQL。

MySQL 集成测试：

```powershell
$env:MYSQL_TEST_URL='jdbc:mysql://127.0.0.1:3306/copper_twin?serverTimezone=Asia/Shanghai'
$env:MYSQL_TEST_USERNAME='copper_twin'
$env:MYSQL_TEST_PASSWORD='请替换为密码'
mvn test -Dtest=MySqlIntegrationTest -Dspring.profiles.active=mysql
```

## 五、前端安装、打包和运行

### 配置后端地址

在 `CopperTwin-Portable` 创建 `.env.local`：

```text
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8080
```

如果前后端通过同一个反向代理提供服务，可设置为 `/api`，并由 Nginx 将 `/api/` 转发到后端。

### Linux/macOS/Windows 通用开发依赖安装

```bash
cd CopperTwin-Portable
corepack enable
pnpm install --frozen-lockfile
pnpm run build
```

如果没有 pnpm，也可以使用 `npm install` 后执行 `npm run build`，但依赖锁定与仓库的 pnpm lockfile 可能不完全一致，生产环境优先使用 pnpm。

### 生产运行

```bash
pnpm run start -- --host 0.0.0.0 --port 4173
```

Windows PowerShell：

```powershell
$env:HOST='0.0.0.0'
$env:PORT='4173'
pnpm run start
```

验证：

```bash
curl -I http://127.0.0.1:4173/
```

仓库内的 `Start-Demo.bat` 是离线演示启动器，使用自带 Node runtime 和开发服务器，不建议作为生产部署方式。

## 六、反向代理示例（Nginx）

```nginx
server {
    listen 80;
    server_name copper.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        proxy_pass http://127.0.0.1:4173;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

使用此配置时，前端 `.env.local` 应设置 `NEXT_PUBLIC_API_BASE_URL=/api`，然后重新执行前端构建。

## 七、服务托管

### Linux systemd 后端

`/etc/systemd/system/copper-twin-backend.service`：

```ini
[Unit]
After=network-online.target

[Service]
User=coppertwin
WorkingDirectory=/opt/coppertwin/backend
EnvironmentFile=/etc/coppertwin/backend.env
ExecStart=/usr/bin/java -jar /opt/coppertwin/backend/target/backend-0.1.0-SNAPSHOT.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now copper-twin-backend
sudo journalctl -u copper-twin-backend -f
```

前端可使用同样方式托管 `pnpm run start`，`WorkingDirectory` 指向 `CopperTwin-Portable`。

### Windows

可使用任务计划程序、NSSM 或 WinSW 托管两个进程。后端程序为 `java.exe -jar target\backend-0.1.0-SNAPSHOT.jar`，前端程序为 `pnpm.cmd run start`；工作目录必须分别指向后端和前端目录，并配置环境变量。

### macOS

可使用 `launchd` 的 LaunchAgent/LaunchDaemon 托管 Node 和 Java 进程；关键配置与 systemd 相同：固定工作目录、环境变量、标准输出日志和异常自动重启。

## 八、升级与回滚

1. 备份 PostgreSQL：`pg_dump -Fc -h host -U user copper_twin > backup.dump`。
2. 拉取目标 Git 分支并查看提交差异。
3. 先执行后端 `mvn test && mvn package`。
4. 停止旧后端，替换 JAR，启动并检查 `/api/v1/health/ready`。
5. 再部署前端并执行 `pnpm run build`。
6. 回滚时恢复上一版 JAR/前端构建，并按数据库迁移的兼容策略恢复备份；不要手工删除已执行的 Flyway 记录。

## 九、备份、日志和安全

- 每日备份 PostgreSQL，定期验证备份可恢复。
- 将 Java 标准输出、Nginx 访问日志和数据库日志纳入日志轮转。
- 生产数据库只允许后端网段访问，不直接暴露到公网。
- 使用 HTTPS，并将 `CORS_ALLOWED_ORIGINS` 限制为实际前端域名。
- 不使用 `application-demo.yml` 作为生产配置；它会使用 H2 内存数据库，重启后数据丢失。

## 十、故障排查

| 现象 | 检查项 |
|---|---|
| 前端页面打不开 | 检查 4173 监听、Node 版本、`pnpm run build` 输出 |
| 前端显示接口错误 | 检查 `NEXT_PUBLIC_API_BASE_URL`、CORS、后端 8080 端口 |
| 后端启动失败 | 检查 Java 17、数据库连接、密码、Flyway 迁移日志 |
| 数据库迁移失败 | 确认目标库版本、是否重复执行完整 SQL、是否有未完成迁移 |
| 页面没有实时数据 | 检查 `/api/v1/health/ready`、测点种子数据和模拟采集脚本 |
| 端口冲突 | Linux 使用 `ss -lntp`，Windows 使用 `Get-NetTCPConnection -State Listen` |

## 十一、模拟数据与接口检查

后端启动后可发送模拟测点：

```powershell
.\scripts\Send-SimulatedReadings.ps1 -Rounds 24 -IntervalSeconds 5
```

然后访问：

- `GET /api/v1/production/process-overview/measurements`
- `GET /api/v1/energy/overview`
- `GET /api/v1/energy/flow?energyCode=ELECTRICITY`

前端页面会按接口配置自动刷新，接口失败时应显示错误或暂无数据提示。

## 十二、甲方演示数据自动生成器

仓库提供 `scripts/generate_demo_data.py`，通过正式的 `/api/v1/ingest/sensor-readings:batch` 接口持续写入合理的演示数据，不直接修改数据库表。

每轮默认发送 42 条数据：10 个工艺测点，以及 16 个能源表的累计量和瞬时量。工艺值带有平滑波动和关联负荷，能源累计量从数据库当前值继续递增，因此趋势、设备状态、能源流向和能耗排行会同步变化。

### Linux/macOS

```bash
cd Git_NTP_TYL_Mid
python3 scripts/generate_demo_data.py --base-url http://127.0.0.1:8080 --interval 10 --scenario showcase
```

### Windows PowerShell

```powershell
cd Git_NTP_TYL_Mid
powershell -ExecutionPolicy Bypass -File scripts\Start-Demo-Data.ps1 `
  -BaseUrl http://127.0.0.1:8080 -IntervalSeconds 10 -Scenario showcase
```

Windows 也可以直接运行 Python：

```powershell
py scripts\generate_demo_data.py --base-url http://127.0.0.1:8080 --interval 10 --scenario showcase
```

参数说明：

- `--rounds 12`：发送 12 轮后自动退出；省略或设为 0 表示持续运行，按 Ctrl+C 停止。
- `--interval 10`：两轮之间间隔 10 秒，应与前端轮询周期匹配。
- `--scenario normal`：只产生正常生产波动。
- `--scenario showcase`：循环展示正常、张力预警、线径报警和参数恢复。
- `--dry-run`：只打印一轮 JSON，不发送到后端。

建议甲方演示前先启动数据库、后端和前端，再运行生成器；演示结束按 Ctrl+C 停止生成器即可。生成器使用 `CUSTOMER_DEMO_GENERATOR` 作为来源标识，重复运行不会覆盖真实采集记录。
